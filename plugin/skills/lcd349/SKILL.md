# lcd349: UIs for the Waveshare ESP32-S3-Touch-LCD-3.49

A product is an ESP-IDF project that depends on the `lcd349` component. It uses LVGL 9 for its UI and the `lcd349_*` C API for everything physical, so the same source builds for the board (`esp32s3`) and for the emulator, which these tools drive. The facts below come from the board's `device.json`; the design rules are the ones `ui_lint` enforces.

## The board at a glance

- **Screen:** 640 × 172 px landscape, about 86 × 23 mm: **7.5 px per mm**. RGB565, so gradients band. Full-frame refresh only: every change redraws the whole screen (about 13 ms a frame), so animation judders.
- **Touch:** 1 point (no pinch, no multi-touch), sampled every 30 ms, only while the display is on. Touch **never** wakes the board.
- **Buttons:** only two: BOOT and PWR. Holding BOOT through a reset enters download mode instead of the product.
- **Wi-Fi:** 2.4 GHz only. **Power:** battery with a software power hold; states `active`, `display_off`, `light_sleep`, `off`, `download`.
- **Wireframe grid:** one character = 8 × 16 px, so the screen is 80 columns × 10 rows (with 12 px to spare).
- In code, use `LCD349_LCD_W`, `LCD349_LCD_H`, `LCD349_MM_TO_PX(mm)` and the `LCD349_RULE_*` constants from `lcd349_board.h`, never copied numbers.

## Design rules (`ui_lint` checks them)

| Rule | Threshold | Why |
|---|---|---|
| `touch-target` (error) | 56 px ≈ 7.5 mm | 56 px is about 7.5 mm at 7.5 px/mm; smaller targets are missed by fingers. |
| `font-min` (error) | 12 px ≈ 1.6 mm | 12 px text is about 1.6 mm tall on this panel; smaller is unreadable at arm's length. |
| `contrast` (error) | 4.5:1 | WCAG AA for normal text; small screens are read at a glance, often outdoors. |
| `clipped-text` (error) | — | Text that doesn't fit is cut off or runs outside its object. |
| `missing-glyph` (error) | — | Characters missing from the font render as nothing or as boxes. |
| `off-screen` (error) | — | Objects outside 640 x 172 are invisible on the device. |
| `overlap` (error) | — | Overlapping click areas make a tap ambiguous. |
| `no-momentum` (error) | — | Every frame is a full-frame flush, so kinetic scrolling judders. |
| `gradient` (warning) | — | Gradients band visibly in RGB565. |

## Workflow

Copy this checklist into your plan and work through it in order:

- [ ] **1. Scaffold.** `new_project` makes a project with one screen, a scenario and its golden; or open the existing project. Read `device_info` (or `references/device.md`) once.
- [ ] **2. Sketch.** Draw each screen as a wireframe on the character grid above, with sizes in pixels, and show it before writing code (see [Wireframes](#wireframes)). Check every touch target and text size against the rules.
- [ ] **3. Build and run.** `build`, then `run` (headless; `run` builds first anyway). Fix compiler errors; a hint names the kit call that replaces an ESP-IDF component the emulator lacks.
- [ ] **4. Check.** `screenshot` and look at it. `ui_tree` for sizes, fonts and colours. `ui_lint` must report 0 errors. Drive it the way a person would: `touch` and `press`, then `wait` for the log line or text that proves it worked.
- [ ] **5. Fix and repeat** until the screen looks right on the screenshot and lint is clean, for every screen and every state (empty, full, error, asleep).
- [ ] **6. Scenario.** Write `tests/<flow>.scenario.yaml` for each flow, with a golden screenshot per screen and a `lint` step per screen (`references/scenarios.md`), and `run_scenario` until it passes. Each run writes the first missing golden and fails at that step: look at each golden before accepting it.
- [ ] **7. Hand over.** Give the user the parts of `references/hardware-checklist.md` that apply: how to flash, what to look at, and everything in `references/fidelity.md` that the product depends on. The emulator doesn't model those; only the board can show them.

Don't call a UI done before step 7, and say plainly which checklist items are still open.

## Buttons and touch: the grammar

- **Short press steps:** move the selection or go to the next item; show a focus ring.
- **Hold commits:** open, approve, confirm. Show the hold filling and act the moment it completes; releasing early cancels. Use the kit's classifier (`lcd349_classifier_*`) for timing.
- **Chord** (both buttons together) is for one rare global action.
- **Visibility guard:** a commit counts only if its press began at least 500 ms after the screen it confirms appeared.
- **Wake-only press:** the press that wakes the board from sleep only wakes it; ignore gestures until both buttons are up.
- **Irreversible actions** need a hold or a confirm dialog whose Cancel has the focus first.
- **Touch** is one point: taps, and swipes along the long axis. No pinch, no long drags, no kinetic scrolling. Touch never wakes the board.
- **Never** design a boot-time combination with BOOT: held through a reset, it enters download mode.

## Never do

- Call `esp_lcd`, `esp_wifi`, `driver/gpio.h`, `driver/ledc.h`, I2C, I2S, ADC, `esp_sleep`, `esp_timer` or USB serial drivers directly. Use the `lcd349_*` API (`references/sdk-api.md`); the build names the replacement when you slip.
- Test `CONFIG_IDF_TARGET` or add target `#if`s in product code. If something differs between the board and the emulator, it belongs in the kit.
- Touch LVGL outside LVGL callbacks or `lcd349_ui_lock()`/`lcd349_ui_unlock()`, or block inside an LVGL or kit callback. Button, touch and Wi-Fi callbacks run on the kit's event task: queue the work to your own task.
- Animate: no transitions, fades, slides, spinners or kinetic scrolling. Give pressable objects a zero-length transition; a NULL transition crashes LVGL 9.6.
- Use gradients, text under the font rule, or text that runs off its object (truncate with dots, or wrap where the height fits every line).
- Copy board numbers into code. Use `LCD349_LCD_W`, `LCD349_LCD_H`, `LCD349_MM_TO_PX()` and the `LCD349_RULE_*` constants.
- Silence a lint finding with an `ignore:<rule>` tag unless the exception is deliberate, and say so in a comment.
- Accept a golden you haven't looked at, or update goldens to make a failing scenario pass without understanding the change.
- Link SDL or open a window in the product; the window is a separate viewer.

## Product code essentials

- Start with `lcd349_init(NULL)`, then build the UI under `lcd349_ui_lock()`. Check `lcd349_board_status()` and degrade gracefully when a subsystem failed.
- Log every user-visible event with `ESP_LOGI` (a tap, a page, an approval): scenarios and `wait` key off log lines.
- Save settings with `lcd349_kv_*` when they change. Read the clock with `lcd349_rtc_get()`, time with `lcd349_time_ms()`.
- Read lines a host tool sends over USB with `lcd349_console_read_line()`, from your own task.
- Recipes for the common screens are in `references/recipes.md`; start from them.
